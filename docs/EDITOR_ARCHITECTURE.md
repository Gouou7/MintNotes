# 编辑器架构原则

[文档索引](README.md)

本文定义 Mint Notes 编辑器必须长期遵循的稳定架构原则，包括目标、权威状态、层次、数据流、源码事务协议、扩展能力和主要权衡。面向用户的语法与交互行为见[用户指南](USER_GUIDE.md)；仓库结构、实现入口和验证命令见[开发指南](DEVELOPMENT.md)。

## 文档定位与治理

本文是编辑器设计契约，不是具体功能说明或实现笔记。任何解析器、序列化器、控制器、编辑器适配器、实时展示或编辑器扩展更改，都必须先阅读并遵循本文。

- 本文只记录跨功能长期成立的设计原则，不累积具体语法、交互边界、布局规则、平台兼容方案或完整验收矩阵。
- 功能变更必须在本文定义的架构内实现。用户可见行为写入用户指南；任务特有的边界由当前需求、针对性测试和必要的代码注释定义。
- 只有在用户明确要求修改编辑器架构原则时，才可编辑本文。仅要求实现、修复、优化或重构编辑器功能，不构成修改本文的授权。
- 如果需求与本文冲突，应把冲突作为架构决策提交给用户，不得通过顺手改写本文来迁就实现，也不得在未获得明确授权时继续采用冲突方案。
- 实现与本文不一致时，应先判断实现缺陷、历史债务或新的架构提案；现有实现不能自动使原则失效。

## 目标与非目标

编辑器架构有以下目标：

1. **保持规范 Markdown 完整可信。**未经用户授权的生命周期和展示工作不得改变文档内容，也不得把语义等价当作字符串相等。
2. **维持单一权威状态。**编辑、历史、持久化、同步和导出都以同一规范 Markdown 为依据，派生结构和展示结果不能成为第二个文档模型。
3. **使用明确的源码事务。**每次由编辑器产生的内容变化都能定位到规范源码范围、结果选区和一个原子撤销单元，不能依赖 DOM 或全文重新序列化猜测用户意图。
4. **保持本地优先。**输入与本地提交不等待网络；服务器同步只能发生在规范内容已进入本地写入路径之后。
5. **允许受控扩展。**产品功能可以识别、展示或显式转换 Markdown，但不能绕过权威状态、事务协议和依赖方向。

本文不规定某种语法的具体呈现、光标按键行为、视觉间距、平台补丁或测试用例清单，也不把某一种内部优化策略永久固定为架构要求。只要不破坏本文契约，这些行为和实现可以按具体任务演进。

## 权威状态与术语

| 术语 | 定义 |
| --- | --- |
| 规范 Markdown | 用户笔记的准确 Markdown 字符串，是唯一权威、可提交、可持久化和可交换的文档模型，也是所有编辑操作的唯一内容目标。 |
| `CanonicalSource` | 编辑器控制器当前接受的规范 Markdown 状态。它表示逻辑权威，不要求内存中只能存在一份相同字符串。 |
| `SourceOffset` | 规范 Markdown 中的字符串边界，以 JavaScript 字符串使用的 UTF-16 码元为单位。所有公开的源码范围必须使用同一坐标定义。 |
| `SourceSelection` | 由规范源码 `anchor` 和 `head` 组成的选区；模式、视图或派生结构变化时仍以该坐标表达。 |
| `SourceTransaction` | 提交编辑器内容变化的唯一协议，包含准确源码编辑、结果选区、来源和必要的派生更新提示。 |
| 派生文档 | 从规范 Markdown 解析得到的结构、源码映射和诊断元数据。它可以销毁和重建，不拥有独立文档权威。 |
| 交互与展示状态 | 选区激活、组合输入缓冲、装饰、节点视图、渲染结果、加载状态、测量值和临时资源。它们不属于 Markdown 内容。 |

“唯一权威状态”是逻辑所有权约束，不是禁止缓存、历史快照或不可变副本。任何副本必须有明确用途，且不能在绕过源码事务的情况下独立演化为另一份当前文档。

解析、验证、重新派生、渲染、选择变化、模式变化和异步展示刷新都是只读过程。它们不得改变 `CanonicalSource`、写入源码历史或发出内容变化通知。

如果某个适配器因外部解析或展示能力限制而需要临时兼容表示，该表示必须满足以下条件：

- 与规范 Markdown 之间具有明确、无歧义且可逆的映射，允许的编辑在该映射下保持闭合；
- 相关源码坐标能够映射回规范 Markdown；
- 每次用户编辑都必须先成功映射并接受为 `SourceTransaction`，之后才能确认该编辑并更新临时表示；
- 绝不进入应用文档状态、编辑撤销历史、应用修订历史、持久化、同步、导出或服务器；
- 无法安全映射的操作必须在接受用户输入前回退到规范源码；不得提交临时表示，也不得静默丢弃已经确认的输入。

## 层次与职责

| 层次 | 主要职责 | 不得承担的职责 |
| --- | --- | --- |
| 应用与保险库层 | 提供规范 Markdown，接收已提交内容，负责持久修订历史、加密、IndexedDB 和后台同步。 | 不得把 ProseMirror 视图、DOM、派生文档或展示结果当作文档内容。 |
| 公共门面与控制器 | 持有活动 `CanonicalSource`、规范选区和编辑撤销历史，验证并原子应用源码事务，对应用提供稳定的类型化 API。 | 不得把内部编辑器视图暴露给应用层，也不得通过网络完成本地编辑。 |
| 编辑器核心与派生层 | 解析规范 Markdown，建立源码坐标映射，维护供实时交互使用的 ProseMirror 派生投影，并把输入意图映射为源码事务。 | 不得拥有另一份可独立提交的文档状态，不得用派生序列化结果覆盖规范源码。 |
| 展示宿主 | 管理装饰、部件、渲染器生命周期、优先级、清理、失败回退和展示刷新。 | 不得修改规范 Markdown、写入源码历史或持久化展示产物。 |
| 产品扩展 | 通过核心契约识别源码、声明展示，或通过类型化命令请求源码事务。 | 不得绕过控制器直接修改派生文档，不得让核心依赖具体产品扩展。 |
| 只读渲染器 | 从规范 Markdown 派生阅读视图，并复用安全的识别器或渲染服务。 | 不得创建可编辑副本或把渲染结果反馈为 Markdown。 |

仓库中的职责映射如下：

- `src/editor/core/` 拥有控制器、规范源码事务、解析与映射、派生编辑状态、通用展示宿主和扩展契约。
- `src/editor/extensions/` 包含相互独立的产品扩展，只依赖核心公开契约。
- `src/editor/` 下的其他模块负责 React 适配、只读渲染和应用侧编辑器集成。
- 保险库模块只使用公共编辑器 API，不接收或保存编辑器内部视图。

依赖方向必须保持为：应用组合核心与扩展，扩展依赖核心契约，核心不导入产品扩展。展示状态只能向界面流动，不能反向成为应用数据。

## 单向数据流

加载与展示：

```text
应用中的规范 Markdown
  -> 编辑器控制器
  -> 解析与源码映射
  -> 派生文档
  -> 展示宿主或只读渲染器
  -> DOM
```

用户编辑：

```text
用户编辑意图
  -> 规范源码范围
  -> SourceTransaction
  -> 新 CanonicalSource、结果选区与编辑撤销历史
  -> 内容变化通知
  -> 应用状态、持久修订历史与本地加密写入
  -> 后台同步

新 CanonicalSource
  -> 更新或重新建立派生文档
  -> 刷新展示
```

仅展示数据刷新：

```text
外部展示数据或异步渲染结果
  -> 展示宿主
  -> DOM
```

以上数据流有以下硬性边界：

- DOM、节点视图文本、渲染器输出、临时资源和派生文档序列化不得反向覆盖规范 Markdown。
- 重新解析、局部更新或完整重建都只是派生策略；它们不能改变事务已经确定的规范内容。
- 阅读模式直接消费规范 Markdown，不创建第二个可编辑模型。
- 初始化通过控制器建立首个规范文档世代，不产生内容变化通知。初始化后的外部全文替换必须通过控制器的显式重置 API 建立新世代，明确设置选区并清除或重建编辑撤销历史；它不得伪装成用户编辑，也不得把外部输入回送为新的 `onChange`。
- 网络请求不在输入和本地提交的关键路径上。

## 源码事务协议

除初始化和显式外部文档世代重置外，所有编辑路径都必须归一为 `SourceTransaction`。其协议遵循以下规则：

1. 本地事务必须在同一次控制器操作中针对当前 `CanonicalSource` 构造并立即应用，不得作为无版本信息的任务排队。事务若跨越异步或外部边界，其提交上下文必须携带可验证的文档世代或等价源码身份；过期事务必须被拒绝，或在应用前经过显式、可验证的重新映射。
2. `edits` 使用事务开始前的规范源码坐标。所有范围必须有效且互不重叠；插入内容按原字符串保留。
3. `selection` 使用事务完成后的规范源码坐标，不能使用派生文档位置作为公共结果。
4. `origin` 和派生更新提示只描述意图与执行策略，不赋予绕过范围验证或内容授权的能力。
5. 一个事务要么整体成功，要么完全不改变规范源码、规范选区和编辑撤销历史。一个显式用户命令对应一个撤销单元。
6. 只有接受后确实改变 `CanonicalSource` 的事务才能发出一次内容变化通知。仅展示事务和无变化事务不得进入编辑撤销历史或触发 `onChange`。
7. 输入法组合等短期交互缓冲可以存在，但只有最终提交的源码事务能够改变规范内容。
8. ProseMirror 文档变化必须携带显式源码事务，或由严格限定且可证明准确的映射转换为源码事务。无法证明安全的变化必须失败关闭。
9. 禁止使用 DOM 文本、差异启发式或完整派生文档序列化作为通用内容恢复路径。
10. 撤销与重做作用于已接受的源码事务；派生重建、展示激活和异步刷新不形成源码撤销记录。
11. `CanonicalSource` 提交后才能更新派生文档。重新解析可以改变结构表示，但不得进一步改写规范源码。

## 扩展能力边界

| 能力类型 | 可以做什么 | 不得做什么 |
| --- | --- | --- |
| 声明式展示 | 读取声明范围内的准确源码和有限语义上下文；返回匹配、稳定身份，以及同步结果或由宿主管理的异步渲染任务。 | 不得接收原始编辑器视图、派发文档事务、修改 Markdown 或持久化展示结果。 |
| 类型化源码命令 | 根据类型化输入和规范源码上下文构造 `SourceTransaction`。 | 不得直接操作 ProseMirror 文档或 DOM，不得绕过控制器提交。 |
| 宿主服务 | 注入附件解析、导航或渲染等外部能力，并把结果交给展示宿主。 | 不得把临时 URL、渲染结构或异步结果写回 Markdown；内容变化仍须使用源码命令。 |
| 遗留底层接口 | 仅用于隔离并迁移现有耦合。 | 新功能不得采用，也不得把它当作扩大扩展权限的先例。 |

扩展系统还必须遵循以下原则：

- 每种产品语法或能力保持为独立扩展，不能形成拥有任意编辑权限的聚合插件。
- 匹配器声明其拥有的准确源码范围；展示宿主验证范围、管理生命周期，并决定何时显示作者源码。
- 展示所有权和重叠冲突必须由显式优先级或明确规则决定；无法唯一决定时失败关闭，不能依赖注册顺序。
- 渲染失败必须回退为安全的作者源码展示，不得影响规范状态。异步渲染契约必须向宿主暴露代际身份、完成、失败、取消和清理，使宿主能够丢弃过期结果并执行回退。
- 展示所需的资源和查询结果默认只存在于内存中；若功能需要改变 Markdown，必须升级为显式源码命令。
- 核心拥有编辑事务、源码映射、展示宿主和生命周期；扩展拥有识别与产品渲染，不反转这一依赖关系。

## 主要权衡

| 选择 | 收益 | 代价与缓解 |
| --- | --- | --- |
| 规范源码优先于语义树 | 保留用户写法和可移植 Markdown，避免静默规范化。 | 源码映射和局部事务更复杂；复杂度集中在控制器与核心，不向应用扩散。 |
| 规范源码坐标优先于 ProseMirror 坐标 | 选区、命令和模式之间具有共同坐标。 | 必须维护可靠映射；应用和产品扩展不得自行解释内部位置。 |
| 局部更新与必要的重新派生并存 | 普通编辑可以保持响应，结构变化仍以重新解析保证正确性。 | 需要判断派生状态何时失效；不确定时可以重新派生，但不能改写源码。 |
| 受限扩展优先于开放内部视图 | 新功能不能绕过权威状态和生命周期，核心保持可维护。 | 扩展自由度较低；通过新增类型化契约解决真实能力缺口，而不是暴露内部对象。 |
| 允许受控兼容适配 | 可以接入不完全理解规范 Markdown 的解析或渲染能力。 | 存在双模型风险；只允许可逆、无歧义、不可持久化且失败安全的边界适配。 |
| 稳定原则与功能细节分离 | 架构契约不随每次交互调整而漂移。 | 具体边界需要在需求、用户指南和测试中保持清楚，不能依赖本文替代功能规格。 |

这些选择意味着：源码正确性高于从派生结构直接编辑的便利，依赖隔离高于扩展获得内部权限的便利，本地提交确定性高于把网络或异步渲染纳入编辑关键路径的便利。

## 编辑器变更准入

开始编辑器功能更改前，必须能够回答以下问题：

1. 哪一层拥有将要改变的状态？
2. 内容变化如何表达为准确、原子的 `SourceTransaction`？
3. 哪些数据只是派生、交互或展示状态，如何保证它们不会进入持久化？
4. 是否保持核心、扩展、应用和只读渲染器之间的依赖方向？
5. 是否保持输入与本地提交不等待网络？
6. 需要用哪些针对性测试和用户文档证明本次具体行为，而不把功能细节写回本文？

出现以下任一情况时，该更改已经构成架构提案，而不是普通功能修改：

- 引入另一份可独立编辑、提交或持久化的文档模型；
- 新增从 DOM、渲染结果或派生序列化回写 Markdown 的路径；
- 绕过 `SourceTransaction` 修改规范内容；
- 把原始编辑器视图暴露给应用或新的产品扩展；
- 让展示状态进入历史、同步、导出或服务器；
- 让输入或本地提交依赖网络结果；
- 改变本文规定的层次、依赖方向、事务协议或扩展权限。

遇到架构提案时，应停止按普通功能变更推进，向用户说明冲突、收益、代价和迁移影响。只有用户明确要求修改原则后，才能更新本文并据此实施。
