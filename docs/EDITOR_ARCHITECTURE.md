# 编辑器架构原则

[文档索引](README.md)

本文规定 Mint Notes 编辑器必须长期遵守的设计边界，主要回答以下问题：什么是笔记正文的唯一来源，各类状态分别由谁持有，用户编辑如何转化为源码修改，派生视图能做什么，以及产品扩展可以获得哪些能力。

面向用户的语法和交互行为见[用户指南](USER_GUIDE.md)；仓库结构、实现入口和验证命令见[开发指南](DEVELOPMENT.md)。

## 如何使用本文

本文是编辑器的设计契约，不是功能说明或实现笔记。修改解析器、序列化器、控制器、编辑器适配器、实时展示或产品扩展前，都必须先阅读并遵守本文。

- 本文只记录跨功能、长期有效的设计原则，不收录具体语法的呈现方式、光标和按键行为、布局规则、平台兼容方案或完整验收矩阵。
- 功能必须在本文规定的边界内实现。用户可见行为写入用户指南；任务特有的边界由当前需求、针对性测试和必要的代码注释说明。
- 只有用户明确要求修改编辑器架构原则时，才能编辑本文。实现、修复、优化或重构某项编辑器功能，不代表可以同时修改这些原则。
- 如果需求与本文冲突，应将其作为架构决策提交给用户，说明冲突、收益和代价。在获得明确授权前，不得通过改写原则迁就实现，也不得继续采用冲突方案。
- 如果当前实现与本文不一致，应先判断它属于实现缺陷、历史债务还是新的架构提案。现有实现不能自动使本文失效。

## 核心原则

以下五项原则必须始终成立：

1. **完整保留用户的 Markdown。**未经用户明确编辑，生命周期管理和展示处理不得改变正文，也不得把语义等价误当成源码字符串相同。
2. **只保留一份权威正文。**编辑、历史、持久化、同步和导出都以同一份规范 Markdown 为准。解析结构和展示结果不能成为第二个文档模型。
3. **通过明确的源码事务提交编辑。**每次内容变化都必须对应准确的源码范围、编辑后的选区和一个原子撤销单元，不能依赖 DOM 或全文重新序列化来猜测用户意图。
4. **始终保持本地优先。**输入和本地提交不得等待网络。只有规范内容进入本地写入路径后，才能开始服务器同步。
5. **只向扩展开放受控能力。**产品功能可以识别、展示或显式转换 Markdown，但不得绕过权威状态、源码事务或既定依赖方向。

本文不固定某一种内部优化方案。只要不破坏以上原则，具体交互和实现方式可以随需求演进。

## 文档状态与基本术语

### 编辑器和编辑模式

“编辑器”统一指负责笔记正文编辑或显示的模块。它接收同一份规范 Markdown，并提供以下三种编辑模式：

- **实时模式**和**源码模式**可以编辑正文。
- **阅读模式**只显示由规范 Markdown 生成的只读内容。

实时模式中的 Markdown 结构还具有 `LiveSyntaxState`：当光标位于某段语法的源码范围内时，该结构处于 `editing`（编辑态）；光标移出后处于 `rendering`（渲染态）。编辑态和渲染态只是实时模式中的交互状态，不是新的编辑模式。

### 规范源码及其坐标

| 术语 | 含义 |
| --- | --- |
| 规范 Markdown | 用户笔记的准确 Markdown 字符串。它是唯一可以提交、持久化和交换的文档内容，也是所有编辑操作的目标。 |
| `CanonicalSource` | 编辑器控制器当前接受的规范 Markdown。它表示正文在逻辑上的唯一权威，并不要求内存中只能存在一份相同的字符串。 |
| `SourceOffset` | 规范 Markdown 中的字符串边界，按 JavaScript 的 UTF-16 码元计数。所有公开的源码范围必须使用这一坐标定义。 |
| `SourceSelection` | 由规范源码中的 `anchor` 和 `head` 组成的选区。切换模式、更新视图或重建派生结构时，选区仍使用源码坐标表示。 |
| `SourceTransaction` | 提交内容变化的唯一协议。它包含准确的源码编辑、编辑后的选区、操作来源，以及必要的派生更新提示。 |

“唯一权威”是对状态所有权的要求，不是禁止缓存、历史快照或不可变副本。每份副本都必须有明确用途，并且不能绕过源码事务，自行演变成另一份当前正文。

### 派生状态和展示状态

规范 Markdown 之外的编辑器状态分为两类：

| 状态 | 包含内容 | 边界 |
| --- | --- | --- |
| 派生文档 | 从规范 Markdown 解析得到的结构、源码映射和诊断元数据。 | 可以随时销毁和重建，不拥有独立的文档权威。 |
| 交互与展示状态 | 编辑态／渲染态切换、输入法组合缓冲、装饰、节点视图、渲染结果、加载状态、测量值和临时资源。 | 不属于 Markdown 正文，不得进入源码历史、持久化或同步。 |

解析、验证、重新派生、渲染、选区变化、模式切换和异步展示刷新都是只读过程。它们不得改变 `CanonicalSource`，不得写入源码历史，也不得发出内容变化通知。

### 临时兼容表示

外部解析器或渲染器有时无法直接处理规范 Markdown。适配器可以为此建立临时兼容表示，但必须同时满足以下条件：

- 它与规范 Markdown 之间的映射必须明确、无歧义且可逆；只允许能够完整映射回规范 Markdown 的编辑。
- 兼容表示中的相关位置必须能够映射回规范源码坐标。
- 每次用户编辑都必须先成功映射为 `SourceTransaction` 并被控制器接受，之后才能确认该编辑并更新兼容表示。
- 兼容表示不得进入应用文档状态、编辑撤销历史、应用修订历史、持久化、同步、导出或服务器。
- 如果某项操作无法安全映射，必须在接受用户输入前回退到规范源码。不得提交兼容表示，也不得静默丢弃已经确认的输入。

## 分层与依赖方向

每一层只持有完成自身职责所需的状态：

| 层次 | 负责什么 | 不能做什么 |
| --- | --- | --- |
| 应用与保险库层 | 提供规范 Markdown，接收已提交内容，管理持久修订历史、加密、IndexedDB 和后台同步。 | 不得把 ProseMirror 视图、DOM、派生文档或展示结果当作正文。 |
| 公共门面与控制器 | 持有当前 `CanonicalSource`、规范选区和编辑撤销历史；验证并原子应用源码事务；向应用提供稳定的类型化 API。 | 不得向应用暴露编辑器内部视图，也不得通过网络完成本地编辑。 |
| 编辑器核心与派生层 | 解析规范 Markdown，建立源码坐标映射，维护实时交互所需的 ProseMirror 派生投影，并把输入意图映射为源码事务。 | 不得持有另一份可以独立提交的正文，也不得用派生文档的序列化结果覆盖规范源码。 |
| 展示宿主 | 管理装饰、部件、渲染器生命周期、优先级、清理、失败回退和展示刷新。 | 不得修改规范 Markdown、写入源码历史或持久化展示产物。 |
| 产品扩展 | 通过核心契约识别源码、声明展示，或通过类型化命令请求源码事务。 | 不得绕过控制器修改派生文档，也不得让核心反向依赖具体产品扩展。 |
| 阅读模式编辑器 | 从规范 Markdown 生成只读内容，并复用安全的识别器或渲染服务。 | 不得创建可编辑副本，也不得把渲染结果转换后写回 Markdown。 |

这些职责在仓库中对应以下位置：

- `src/editor/core/`：控制器、规范源码事务、解析与映射、派生编辑状态、通用展示宿主和扩展契约。
- `src/editor/extensions/`：相互独立的产品扩展，只依赖核心公开契约。
- `src/editor/` 下的其他模块：React 适配、实时／源码／阅读三种模式编辑器，以及应用侧编辑器集成。
- 保险库模块：只使用公共编辑器 API，不接收或保存编辑器内部视图。

依赖方向必须保持为：**应用组合核心与扩展，扩展依赖核心契约，核心不导入产品扩展。**展示状态只能流向界面，不能反向成为应用数据。

## 单向数据流

### 加载和展示

```text
应用中的规范 Markdown
  -> 编辑器控制器
  -> 解析与源码映射
  -> 派生文档
  -> 展示宿主或阅读模式编辑器
  -> DOM
```

### 用户编辑

```text
用户编辑意图
  -> 规范源码范围
  -> SourceTransaction
  -> 新 CanonicalSource、结果选区与编辑撤销历史
  -> 内容变化通知
  -> 应用状态、持久修订历史与本地加密写入
  -> 后台同步

新 CanonicalSource
  -> 更新或重新建立派生文档
  -> 刷新展示
```

### 仅刷新展示

```text
外部展示数据或异步渲染结果
  -> 展示宿主
  -> DOM
```

以上流程必须遵守以下边界：

- DOM、节点视图文本、渲染器输出、临时资源和派生文档的序列化结果，都不得反向覆盖规范 Markdown。
- 局部更新、重新解析和完整重建只是维护派生状态的不同策略，不能改变源码事务已经确定的正文。
- 实时模式在编辑态和渲染态之间切换时，只更新交互与展示状态，不发出内容变化通知，也不写入源码撤销历史。
- 阅读模式直接使用规范 Markdown 生成只读内容，不创建第二个可编辑模型。
- 网络请求不得进入输入和本地提交的关键路径。

### 初始化和外部重置

编辑器初始化时，控制器根据输入建立第一个规范文档世代，不发出内容变化通知。

初始化完成后，如果应用需要替换整篇文档，必须调用控制器提供的显式重置 API，建立新的文档世代，明确设置选区，并清除或重建编辑撤销历史。外部重置不能伪装成用户编辑，也不能把外部输入再次通过 `onChange` 回送给应用。

## 源码事务协议

除初始化和显式的外部文档重置外，所有编辑路径最终都必须形成一个 `SourceTransaction`。

### 构造事务

- 本地事务必须针对当前 `CanonicalSource`，在同一次控制器操作中构造并立即应用，不能作为缺少版本信息的任务排队。
- 如果事务跨越异步或外部边界，提交上下文必须携带可验证的文档世代或等价的源码身份。过期事务必须被拒绝；需要继续应用时，必须先经过显式且可验证的重新映射。
- `edits` 使用事务开始前的规范源码坐标。所有范围必须有效且互不重叠，插入内容按原字符串保留。
- `selection` 使用事务完成后的规范源码坐标，不能以派生文档位置作为公开结果。
- `origin` 和派生更新提示只用于描述操作意图和执行策略，不能用来绕过范围验证或内容授权。

### 提交、通知和历史

- 一个事务必须整体成功或整体失败。失败时，规范源码、规范选区和编辑撤销历史都不能发生变化。
- 一个明确的用户命令对应一个撤销单元。
- 只有被接受且确实改变 `CanonicalSource` 的事务，才能发出一次内容变化通知。仅影响展示的事务和没有造成变化的事务不得进入编辑撤销历史，也不得触发 `onChange`。
- 撤销和重做只作用于已经接受的源码事务。派生重建、编辑态／渲染态切换和异步刷新不形成源码撤销记录。
- 必须先提交新的 `CanonicalSource`，再更新派生文档。重新解析可以改变结构表示，但不能进一步改写规范源码。

### 输入法和编辑器适配

- 输入法组合等短期缓冲可以暂时存在，但只有最终提交的源码事务能够改变规范内容。
- ProseMirror 文档变化必须携带明确的源码事务，或者通过严格限定且能够证明准确的映射转换为源码事务。无法证明转换安全时，必须拒绝该变化。
- 不得把 DOM 文本、差异启发式或完整派生文档序列化作为通用的内容恢复方式。

## 扩展能力边界

核心负责源码映射、编辑事务、展示宿主和生命周期；扩展负责识别产品语法并提供对应的展示或类型化命令。扩展只能使用核心公开的受控能力。

| 能力类型 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| 声明式展示 | 读取声明范围内的准确源码和有限语义上下文；返回匹配结果、稳定身份，以及同步结果或由宿主管理的异步渲染任务。 | 不得接收原始编辑器视图、派发文档事务、修改 Markdown 或持久化展示结果。 |
| 类型化源码命令 | 根据类型化输入和规范源码上下文构造 `SourceTransaction`。 | 不得直接操作 ProseMirror 文档或 DOM，也不得绕过控制器提交。 |
| 宿主服务 | 注入附件解析、导航或渲染等外部能力，并将结果交给展示宿主。 | 不得把临时 URL、渲染结构或异步结果写回 Markdown；任何内容变化仍须使用源码命令。 |
| 遗留底层接口 | 仅用于隔离并迁移现有耦合。 | 新功能不得采用，也不得将其作为扩大扩展权限的先例。 |

扩展的注册和运行还必须遵守以下规则：

- 每种产品语法或能力保持为独立扩展，不能形成拥有任意编辑权限的聚合插件。
- 匹配器必须声明自己负责的准确源码范围。展示宿主负责验证范围、管理生命周期，并决定何时显示用户编写的源码。
- 展示所有权和范围重叠必须通过明确的优先级或规则解决。无法唯一确定时应拒绝展示，不能依赖注册顺序碰巧得出结果。
- 渲染失败时，必须安全地回退为用户编写的源码，不能影响规范状态。异步渲染契约必须向宿主提供代际身份以及完成、失败、取消和清理能力，使宿主可以丢弃过期结果并执行回退。
- 展示所需的资源和查询结果默认只保存在内存中。如果功能需要改变 Markdown，必须改为调用明确的源码命令。
- 不得反转依赖关系：核心拥有通用机制，扩展拥有产品识别和渲染逻辑。

## 主要权衡

| 设计选择 | 带来的好处 | 代价和处理方式 |
| --- | --- | --- |
| 规范源码优先于语义树 | 保留用户原有写法和可移植的 Markdown，避免静默规范化。 | 源码映射和局部事务更复杂；这部分复杂度应集中在控制器和核心中，不能向应用层扩散。 |
| 规范源码坐标优先于 ProseMirror 坐标 | 选区、命令和不同编辑模式可以共用同一套坐标。 | 必须维护可靠的坐标映射；应用和产品扩展不得自行解释内部位置。 |
| 同时支持局部更新和必要的重新派生 | 普通编辑可以保持响应，结构变化时仍可通过重新解析保证正确性。 | 实现必须判断派生状态何时失效；如果无法确定，可以重新派生，但不能借此改写源码。 |
| 受限扩展优先于开放内部视图 | 新功能无法绕过权威状态和生命周期，核心也更容易维护。 | 扩展的自由度较低；遇到真实能力缺口时，应新增类型化契约，而不是暴露内部对象。 |
| 允许受控的兼容适配 | 可以接入不能完整理解规范 Markdown 的解析或渲染能力。 | 兼容表示可能形成双模型；因此只允许无歧义、可逆、不持久化且能够安全失败的适配。 |
| 稳定原则与功能细节分开维护 | 架构契约不会随每次交互调整而漂移。 | 具体行为必须在当前需求、用户指南和针对性测试中写清楚，不能用本文代替功能规格。 |

这些选择共同表达了一组优先级：源码正确性高于直接编辑派生结构的便利，依赖隔离高于扩展获取内部权限的便利，本地提交的确定性高于将网络或异步渲染纳入编辑关键路径的便利。

## 编辑器变更准入

### 开始修改前

开始编辑器功能更改前，必须能够回答以下问题：

1. 将要改变的状态由哪一层持有？
2. 内容变化如何表示为准确且原子的 `SourceTransaction`？
3. 哪些数据只是派生、交互或展示状态？如何保证它们不会进入持久化？
4. 是否仍然保持核心、扩展、应用和阅读模式编辑器之间的依赖方向？
5. 输入和本地提交是否仍然不等待网络？
6. 应使用哪些针对性测试和用户文档说明本次具体行为，而不把功能细节写回本文？

### 哪些更改属于架构提案

出现以下任一情况时，这项更改已经超出普通功能修改的范围：

- 引入另一份可以独立编辑、提交或持久化的文档模型；
- 新增从 DOM、渲染结果或派生文档序列化结果回写 Markdown 的路径；
- 绕过 `SourceTransaction` 修改规范内容；
- 向应用或新的产品扩展暴露原始编辑器视图；
- 让展示状态进入历史、同步、导出或服务器；
- 让输入或本地提交依赖网络结果；
- 改变本文规定的层次、依赖方向、事务协议或扩展权限。

遇到以上情况时，必须停止按普通功能变更推进，并向用户说明冲突、收益、代价和迁移影响。只有用户明确要求修改本文后，才能更新架构原则并据此实施。
